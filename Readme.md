### Direct response to R25

R25 (AY 2025–26 onward) exists in two versions for CSE (AI&ML): **Affiliated
Colleges** and **University Constituent Colleges**. They disagree with each
other:

- **DevOps:** Affiliated keeps DevOps as a 3-credit Professional Core
  (course code CS503PC) — but that's *general CSE*, not CSE(AI&ML).
  Constituent Colleges reduces it to a 1-credit Skill Development Course lab
  in III Year II Semester. Our own R22 baseline doesn't have standalone
  DevOps at all — it's bundled into AM606PC, a 2-credit "Mini
  Project/Internship/SDC(DevOps)" slot (confirmed against the official R22
  PDF). **We agree with the direction of the Constituent version** — for our
  branch, that's a 2 → 1 move, not 3 → 1. See "the trap" below.
- **Deep Learning:** Constituent Colleges makes it a 4-credit core
  (3-1-0-4, with a tutorial hour) in III-II, ahead of Generative AI in IV-I.
  **We agree with this sequencing** and adopt it.
- **Agentic AI:** R25 Constituent lists Agentic AI and Large Language Models
  as III-I Professional Electives (optional). **We disagree and go
  further** — we make Agentic AI a mandatory IV-II core, because it was the
  single most repeated, unprompted request in our practitioner interview.

### The trap we were told to avoid, and how we avoided it

The assignment specifically warns against citing the Affiliated Colleges R25
document (DevOps still 3 credits) when the intended reference point is the
Constituent Colleges document (DevOps reduced to 1 credit). Both PDFs exist
on JNTUH-affiliated domains and can look interchangeable at a glance. We
fetched both directly:

- Affiliated: `https://jntuh.ac.in/uploads/bulletins/R25B.Tech.CSEIIIYearSyllabus.pdf` — lists `CS503PC DevOps 3 0 0 3` under III Year I Semester.
- University Constituent Colleges: `https://jntuhcem.ac.in/web/notifications/475_R25B.Tech.AIMLConstituent.pdf` — lists `SDC Skill Development Course – 4 (DevOps) 0 0 2 1` under III Year II Semester.

We used the Constituent Colleges document as the basis for Section 6/7, and
call this out explicitly in Section 7 ("Reality check") as the AI-verification
example, because it is exactly the kind of mix-up a model (or a student
skimming search results) could make silently. A second, subtler version of
the same trap: it's tempting to compare R25's DevOps figure straight against
a *guessed* R22 baseline. The real R22 AI&ML baseline (AM606PC, 2 credits,
bundled with Mini Project/Internship) only surfaced when we pulled the full
official R22 PDF and checked every course code — see Section 2.

## 7. Reality check & falsification

**What would disprove this proposal:** if placement outcomes over the next
two admission cycles showed R22-degree graduates matching R25/2030-style
graduates on production-deployment interview rounds at the same rate — i.e.
the MLOps/GenAI gap named by our interviewee didn't actually show up in
hiring outcomes — that would undercut the case for reallocating credits
toward it.

**An assumption we changed our mind about:** we initially assumed the
curriculum's problem was "not enough AI" and planned to just add Generative
AI and Agentic AI on top of R22. The interview reframed this: R22 already
has substantial AI content. The real gap is the missing middle layer between
a trained model and a dependable product — which argues for *reallocation*
(cutting ATCD, KRR, Nature-Inspired Computing, and a reduced DevOps) rather
than pure addition. This is why Section 6 is a swap, not a top-up.

**Documents we could not access:** a JNTU Sultanpur college-specific
syllabus variant (if one exists separately from the university-wide R22
PDF), and internal placement-cell data on where R22 graduates actually get
rejected in interviews. Both would sharpen Section 5 beyond three public
job postings.

**An AI claim we verified independently:** see "The trap" in Section 6 —
an early, unverified answer about "the R25 DevOps credit change" could
easily have cited whichever R25 PDF a search happened to surface first. The
Affiliated and Constituent Colleges versions disagree (3 credits vs. 1
credit) on the exact course this assignment's "critical trap" warning is
about. We resolved it by fetching both PDFs directly and checking the course
code and credit line ourselves rather than trusting a single search result.

**1. Data Structures Lab — singly linked list (Create/Insert/Delete/Traverse)**

*Brief:* "Write a program that uses functions to perform the following
operations on a singly linked list: i) Creation ii) Insertion iii) Deletion
iv) Traversal."

```c
#include <stdio.h>
#include <stdlib.h>

struct Node { int data; struct Node *next; };
struct Node *head = NULL;

void insert(int val) {
    struct Node *n = malloc(sizeof(struct Node));
    n->data = val; n->next = NULL;
    if (head == NULL) { head = n; return; }
    struct Node *t = head;
    while (t->next != NULL) t = t->next;
    t->next = n;
}

void delete(int val) {
    struct Node *cur = head, *prev = NULL;
    while (cur != NULL && cur->data != val) { prev = cur; cur = cur->next; }
    if (cur == NULL) return;
    if (prev == NULL) head = cur->next; else prev->next = cur->next;
    free(cur);
}

void traverse() {
    struct Node *t = head;
    while (t != NULL) { printf("%d -> ", t->data); t = t->next; }
    printf("NULL\n");
}

int main() {
    insert(10); insert(20); insert(30);
    traverse();
    delete(20);
    traverse();
    return 0;
}
```

- **(a) Passed automatically:** creation, tail insertion, value-based
  deletion, and traversal all compiled and ran correctly for the values
  tried.
- **(b) A human still needs to:** add a NULL-check after `malloc` (silently
  crashes on allocation failure otherwise); decide what "insertion" means —
  the brief doesn't say where, so this pass defaulted to tail-insert only,
  with no head/position-insert option; and add a message when `delete` is
  called on a value that isn't in the list, which currently fails silently.

**3. Operating Systems Lab — FCFS CPU scheduling**

*Brief:* "Write a C program to simulate the FCFS CPU scheduling algorithm"
given each process's arrival time and burst time.

```c
#include <stdio.h>

int main() {
    int n = 3;
    int arrival[] = {0, 1, 2};
    int burst[] = {5, 3, 8};
    int completion[3], waiting[3], turnaround[3];
    int time = 0;

    for (int i = 0; i < n; i++) {
        if (time < arrival[i]) time = arrival[i];
        time += burst[i];
        completion[i] = time;
        turnaround[i] = completion[i] - arrival[i];
        waiting[i] = turnaround[i] - burst[i];
    }

    float totalWT = 0, totalTAT = 0;
    for (int i = 0; i < n; i++) {
        printf("P%d  CT=%d  TAT=%d  WT=%d\n", i + 1, completion[i], turnaround[i], waiting[i]);
        totalWT += waiting[i]; totalTAT += turnaround[i];
    }
    printf("Avg WT = %.2f, Avg TAT = %.2f\n", totalWT / n, totalTAT / n);
    return 0;
}
```

- **(a) Passed automatically:** the completion/turnaround/waiting-time
  formulas and the average calculations are correct.
- **(b) A human still needs to:** notice that processes are scheduled in
  **input order**, not sorted by arrival time first. This happens to give
  the right answer for this specific test data (arrival times already
  ascending), but is wrong FCFS behaviour in general — a human running it
  against unsorted input would need to add a sort-by-arrival-time step
  before the loop.

**4. Machine Learning Lab — Linear Regression + evaluation**

*Brief:* "Supervised Learning and Regression Algorithms" — implement Linear
Regression on a given dataset and report Mean Squared Error.

```python
import numpy as np

def linear_regression(X, y):
    X_b = np.c_[np.ones((X.shape[0], 1)), X]
    theta = np.linalg.inv(X_b.T @ X_b) @ X_b.T @ y
    return theta

def predict(X, theta):
    X_b = np.c_[np.ones((X.shape[0], 1)), X]
    return X_b @ theta

def mse(y_true, y_pred):
    return np.mean((y_true - y_pred) ** 2)

X = np.array([[1], [2], [3], [4], [5]])
y = np.array([3, 5, 7, 9, 11])

theta = linear_regression(X, y)
preds = predict(X, theta)
print("MSE:", mse(y, preds))
```

- **(a) Passed automatically:** the normal-equation math (bias term
  included) and the MSE formula are both correct.
- **(b) A human still needs to:** notice this evaluates MSE on the **same
  data it trained on** — there's no train/test split, so the reported error
  quietly overstates how good the model actually is. This is exactly the
  gap our interviewee described ("checking whether its output is reliable")
  — the code runs and produces a number, but the number means less than it
  looks like it does, and only a human checking the methodology (not the
  math) would catch it.

**5. Java (OOP) Lab — traffic-light simulator**

*Brief:* "Write a Java program that simulates a traffic light. The program
lets the user select one of three lights: red, yellow, or green with radio
buttons... Initially, there is no message shown."

```java
import javax.swing.*;
import java.awt.*;
import java.awt.event.*;

public class TrafficLight extends JFrame {
    JLabel message = new JLabel("");
    public TrafficLight() {
        JRadioButton red = new JRadioButton("Red");
        JRadioButton yellow = new JRadioButton("Yellow");
        JRadioButton green = new JRadioButton("Green");

        red.addActionListener(e -> { message.setText("Stop"); message.setForeground(Color.RED); });
        yellow.addActionListener(e -> { message.setText("Ready"); message.setForeground(Color.ORANGE); });
        green.addActionListener(e -> { message.setText("Go"); message.setForeground(Color.GREEN); });

        setLayout(new FlowLayout());
        add(message); add(red); add(yellow); add(green);
        setSize(300, 150);
        setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
        setVisible(true);
    }
    public static void main(String[] args) { new TrafficLight(); }
}
```

- **(a) Passed automatically:** the event handlers correctly update the
  label's text and color per button, and no message shows before any
  button is clicked, matching the brief.
- **(b) A human still needs to:** notice the three `JRadioButton`s are
  never wrapped in a `ButtonGroup` — so nothing stops a user clicking more
  than one at once, which breaks the "select **one** of three" requirement.
  This is invisible reading the code; a human running the GUI would catch
  it in about five seconds by clicking two buttons.

### Task B — One 20-Minute Conversation

**Status: complete.** Full transcript below, condensed on the live site.

**Who we talked to:** A recent JNTU Sultanpur CSE (AI&ML) graduate, now
working as an AI/Software Engineer.

**Purpose:** reviewing the current CSE (AI&ML) curriculum for this challenge
and asking what was useful in industry, what was missing, and what should
change for students graduating around 2030.

1. **What did you have to learn after graduation that college didn't
   teach?** Production-level MLOps and system design. College projects use
   clean datasets and notebooks; industry work involves messy data,
   pipelines, deployment, monitoring, cloud platforms, Docker and
   Kubernetes. College teaches students to build models; industry also
   requires keeping those models running reliably in real systems.

2. **Which subjects from the degree have actually been useful?** Linear
   Algebra, Probability and Statistics, DSA, and Design and Analysis of
   Algorithms — mathematical foundations help with debugging ML systems;
   DSA remains important for technical interviews. Compiler Design/ATCD was
   less directly useful, though not something to remove outright — more a
   question of how much depth and assessment weight it should get in an
   AI-focused programme.

3. **What skills should definitely be in the curriculum for 2030
   graduates?** Stronger coverage of Generative AI, LLMs, RAG, AI-agent
   systems and AI system architecture — students will increasingly need to
   design and orchestrate AI-based systems, not just train conventional
   models.

4. **What do companies expect from freshers that the curriculum doesn't
   prepare them for?** Git/GitHub collaboration, working in teams,
   deployment, and business context — translating a business problem into
   a technical/AI solution, collaborating with modern software workflows,
   and understanding whether deploying a model actually creates business
   value.

5. **If you could reduce one subject and replace it with something else,
   what would you change?** Reduce the emphasis on Automata Theory and
   Compiler Design (ATCD) for an AI&ML-focused programme, and use some of
   that space for a practical Generative AI/LLM and MLOps component —
   reallocation rather than simply adding more subjects.

6. **What do students misunderstand about getting an AI/ML job?** That a
   high Kaggle score or knowing many ML algorithms is enough to be
   job-ready. Industry work involves far more data preparation,
   engineering, debugging, deployment and integration with larger software
   systems than academic ML projects typically expose.

7. **What did you expect to be important in college but later discover
   wasn't?** Memorising and implementing ML algorithms from scratch.
   Industry engineers generally use established libraries (scikit-learn,
   PyTorch, TensorFlow); the more valuable skill is knowing when and why to
   use a method, checking whether its output is reliable, debugging
   failures, and integrating it into a larger system.

**Unexpected insight:** writing ML algorithms from scratch — which feels
like the serious academic skill — was described as having very little
day-to-day value in industry. What mattered more was knowing when to use an
algorithm, how to verify its output, and how to make the resulting system
work reliably in production.

**Key takeaway:** the curriculum problem isn't "needs more AI" — R22 already
has a lot of AI content. The real gap is the transition from learning
individual models to engineering, evaluating, deploying and maintaining AI
*systems*. That reframing is the reason Section 6 is a like-for-like swap
rather than a simple addition.
